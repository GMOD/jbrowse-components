## Changes since v4.3.0

The release notes above cover the highlights. This is the list of changes since
v4.3.0, grouped by area — opening with the rendering rewrite the notes lead
with, and closing with what was removed. A feature that arrived over many
commits is written once, as the thing it ended up being. Bug fixes, internal
refactors and build tooling are not listed individually, except where a fix
changed what the browser does or what a plugin can call; the performance section
below names the headline wins, and the
[optimization guide](https://jbrowse.org/jb2/docs/developer_guides/optimizations)
carries the measurement work behind them. The work landed on main directly
rather than through pull requests, so
[the commit range](https://github.com/GMOD/jbrowse-components/compare/v4.3.0...v5.0.0)
is the complete record.

### Rendering and data flow

The change the release notes lead with, written once as the thing it ended up
being. The runtime half of it — capability probing, out-of-memory handling, the
Canvas2D escape from a lost context — is under
[GPU, errors and diagnostics](#gpu-errors-and-diagnostics).

#### The three backends

- WebGPU, then WebGL2, then Canvas2D, picked at runtime behind one hardware
  abstraction layer, so a display is written once and drawn by whichever the
  browser offers
- every canvas display ships a Canvas2D draw function, and the SVG export of
  most of them runs that same function, so an exported figure matches the screen
- shaders are Slang, compiled to both GPU backends by `pnpm gen:shaders`, with
  the Canvas2D twin of each scalar decision generated from the same source
  instead of kept by hand alongside it — topology and blend state, the
  append-at-a-time instance writers and the per-element uniform setters included
- one copy of the shared band passes, so the alignments coverage band and the
  MAF one draw their shared marks from the same shaders
- the MSAA sample count is a per-display property, since the displays whose
  fragments compute their own coverage get nothing from a multisampled target
  and it is the largest per-display allocation there is
- `@jbrowse/render-core` is a leaf package — mobx, MST and a React peer, with no
  dependency on `@jbrowse/core` — so a display outside the tree can build on it
  directly

#### How data reaches them

- adapters fetch and parse in an RPC worker; the main thread uploads the result
  once and then redraws it every frame. A pan or a zoom is a redraw rather than
  a refetch, which is where the smoothness comes from
- worker output is absolute genomic bp, never pixels and never region-relative,
  so nothing downstream has to be told which viewport it was computed against.
  Hi-C and LD were the last two on fetch-time pixel space and moved with it,
  retiring `StaleViewportRescaleMixin` and the staleness axis it existed for
- two fetch foundations cover every linear display — one per region, one over
  the whole dataset — with three helpers on top: fetch each region, fetch all
  regions in one call, and `fetchRegionsBatched` for a payload covering a set
  the display picked for itself
- one `installUpload` covers the per-region, keyed and global render lifecycles,
  in place of a hand-rolled installer for each
- one `displayPhase` getter per display names its terminal state — loading,
  error, too large, canceled, ready, and a render error where there is a backend
  to fail. It is what the display chrome draws and what the SVG export gates on
- the too-large decision is one measurement path, taken inside the fetch against
  a byte budget, and the banner is derived rather than set, so it releases
  itself when the view moves back under budget instead of sticking or flickering
- a settings change — a color-by, a filter, a height mode — keeps the data
  already on screen drawn under a scrim of its own while the refetch runs. Every
  display but canvas used to blank for the debounce and the round trip to get
  the scrim it could have had over its own data

### Performance

The
[optimization guide](https://jbrowse.org/jb2/docs/developer_guides/optimizations)
has reproducers for the headline numbers here, along with what is still slow and
the directions that measured null.

#### The frame

- a pan, a zoom, a recolor, a re-sort and a resize are shader-parameter changes
  over data already on the card. Zooming into a 1000x long-read pileup was a
  15,321 ms refetch in 4.3.0 and is a 50 ms redraw — read that as work skipped
  rather than work done faster, since the new view is a strict subset of the
  reads the card is already holding
- positions cross the worker boundary as absolute genomic `uint32`, cut into a
  high and a low half a float32 shader can each hold exactly, so a coordinate
  stays exact to 4.29 Gbp where a one-step conversion loses precision above
  about 16 Mbp
- the coordinate ruler was most of the DOM churn in a zoom: keyed by base
  position, a pan reused every node and a zoom rebuilt them all. Positional keys
  take the structural mutations in a 5× zoom from 535 to 248, trading them for
  cheaper attribute patches on nodes that survive
- a render census — a per-component reaction count taken off a MobX spy, beside
  a MutationObserver tally of where the churn lands, so an arm needs no browser
  and no instrumented build — found the same keying in `PaddingBlocks`, at 240
  structural mutations over a 20-frame zoom across four tracks against 12
  positionally keyed. Mid-contig, where a reader spends nearly all of a session,
  there is no seam to mask at all: the empty case returns one shared array now,
  so the component and its transform wrapper leave the frame entirely — 761
  observer renders to 489, and 63.9 DOM mutations a frame to 50.5
- the two arc displays rendered one observer per visible arc, each rebuilding
  its own path and patching its own attributes every frame, per track. It draws
  to one canvas now, with the hover answered by a canvas hit test that ranks
  arcs the way the alignments read-connection band does, so the per-arc terms
  are gone rather than smaller: 26.5 renders a frame to 19.5, and 240
  arc-display DOM mutations to zero at four arcs, where an SV callset carries
  thousands
- two computeds that rebuilt an identical answer every frame. A 1px track-height
  drag re-placed every read and re-baked every color, because the fit budget
  reached the layout as pixels; it arrives as a row cap now, so a drag reuses
  every placement and every GPU buffer until it actually crosses a row. The
  sashimi junction merge answers to the loaded data rather than to the pan, and
  now sits behind the projection instead of inside it
- one MUI wrapper per row off the hierarchical track selector, so 1000 tracks
  mount in 1,460 ms rather than 1,656 ms. Three model-side optimizations
  measured null and are recorded so nobody spends a second session on them
- a pan's GPU buffer churn is one allocation per fetch rather than one per
  frame, and the alignments renderer re-uploads only the arc passes when only
  the arcs or their width changed — about 6.8 ms per region a drag frame at
  10,000 reads, and over 70 ms at 30,000
- a CRAM record is the feature rather than a wrapper around one, and the
  ultra-long-feature LRU beside it is gone: one cache budget covers CRAM too,
  now that the library weighs its records in bytes
- selecting a feature in one track no longer repacks and re-uploads every lane
  of a multi-way synteny display, which does not draw that highlight
- the gridlines overlay gets its own compositor layer

#### The fetch

- BGZF decompression is 70-90% of a cold query, and runs through libdeflate
  compiled to wasm on a four-worker pool — 1.95x end to end on BAM, over a
  22-view pan and zoom across 1000x long-read data
- an index says what a region costs before anything downloads it, in tenths of a
  millisecond, which is what lets the too-large gate answer before the query is
  issued
- a whole-genome BigWig read hands every region to the library at once, so a
  block two regions both asked for is dropped and neighbouring ones merge into
  one request, instead of a round trip per region
- `jbrowse make-pif` writes a coarse copy of each alignment without its CIGAR.
  One whole-genome pass over a human-vs-mouse chain is 1.31 MB in 6 range
  requests off the coarse tier, against 64.23 MB in 22 off the fine one
- a pan that outruns its data aborts the reads for regions already off screen.
  On a four-hop burst throttled to 50 KiB/s that abandoned ~19.5 MiB which would
  otherwise have arrived in full and been thrown away
- the GFF3 redispatch bound asks whether a record can have children rather than
  whether its type is on a list of landmarks. Every NCBI `GCF_*_genomic.gff.gz`
  opens each reference with a chromosome-long `match` record no list names, so
  every query inside that span read the whole chromosome: one 1 kb window at 60
  Mb on the human file parsed 193,008 lines, and parses 63 now
- `jbrowse make-pif` threads its bgzip stage and stops sorting on the CIGAR
  column, taking a 66 MB T2T-vs-GRCh38 PAF from 6.5 s to 3.7 s for the same
  output lines

#### The bundle

- six eager-bundle pins, each the same mistake at a different scale — a module
  that must be evaluated eagerly naming a React component. The first five took
  the sparsest build-your-own page from 347 eager chunks and 667 KB gzipped to
  181 and 464 KB
- the bgzf worker pool is reached through a dynamic import, since that package
  inlines its worker as base64: 141 bytes plus a chunk fetched once a
  bgzip-backed track opens, against 23.4 KB gzipped pinned into every entry
  point that could reach it
- most view and display state models are registered as lazy loaders, which takes
  the model subgraphs out of the initial download: an empty linear-genome-view
  page is 584 KB gzipped rather than 796 KB, and one with four tracks 1,102 KB
  rather than 1,193 KB. What a plugin author has to do differently is under
  [Plugin API](#plugin-api)
- the web entry script stops carrying the MST fork and mobx, a realm with no
  runtime plugins does not fetch the plugin ABI at all, and the RPC worker is
  served a React-free one

#### The mark display

- `LinearMarkDisplay`, in a new marks plugin, draws bars, points and spans from
  a `marks` config slot: each mark names a shape and, per channel — y, color,
  glyph, row — a feature field or a jexl expression, evaluated once in the
  worker. The axis, the legend, the hover and the SVG export all derive from
  that declaration, and the display attaches to feature, alignments and variant
  tracks
- a mark's transform steps run in the worker before it encodes — filter, bin,
  aggregate, coverage, formula, flatten (one feature per subfeature) and stack
  (a greedy first-fit pileup) — and a bin width of `auto` follows the zoom on a
  1/2/5 ladder, refetching only when it crosses a rung
- a mark names the zoom range it draws in, so a binned density mark zoomed out
  and a feature mark zoomed in share one config and one fetch; a mark declaring
  `source: 'density'` draws the density sidecar where the too-large gate refuses
  the features
- color and glyph take a categorical scale over a field, deriving each value's
  entry from the value itself so two regions agree on every value they share,
  and a linear or log color ramp resolves on the main thread, so a pan that

### AI agents and MCP

New in v5.0.0: an agent drives the JBrowse you already have open, rather than
writing a config for you to load. The docs are five pages, starting at
[Using JBrowse with AI agents](https://jbrowse.org/jb2/docs/agents).

- JBrowse Desktop serves an MCP server on a per-user local socket, reached by
  pointing a client at the app binary with the `--mcp` argument. Four tools:
  `run_javascript` runs an async function body inside the app against the live
  session, `screenshot` captures the window or a cropped selector, `open` loads
  a config, a saved session or a hosted genome, and `docs` serves the reference
  bundled into the app — every state model and config type, written by the same
  `autogen` pass as the website's reference pages, so the two cannot drift
- `jb`, the standard library those calls are written against, is published on
  `window` by JBrowse Web too, so the same code runs from a browser agent with
  nothing installed. It covers orientation (`sessionSummary`, `inspect`,
  `listTracks`), building (`loadSessionSpec`, `addTrack`), reading
  (`getFeatures`, `visibleRegions`), restyling (`describeSlots`, beside
  `track.applyDisplaySettings`) and waiting (`waitReady`)
- **Help → Connect an AI agent...** in Desktop shows the client configuration
  for the running install, with a copy button for each form, and says so when
  `JBROWSE_DISABLE_MCP` has turned the server off
- the other four pages are a
  [live model guide](https://jbrowse.org/jb2/docs/agents_live_model),
  [recipes](https://jbrowse.org/jb2/docs/agents_recipes) verified against the
  app before they were written down,
  [hosted genomes and tracks](https://jbrowse.org/jb2/docs/agents_hosted_data)
  and [screenshots from a script](https://jbrowse.org/jb2/docs/agents_capture).
  Inside Desktop the first three are `docs` topics, so an agent never has to
  leave the app to read them
- `run_javascript` is arbitrary code execution in a renderer with Node access,
  deliberately. The guard is the transport — a per-user local socket — so it is
  a desktop-only surface, and it is not in JBrowse Web
- **Help → Connect an AI agent...** reaches Windows and Linux, where it had been
  on the macOS menu alone
- `run_javascript` hands its code an abort signal that fires at the timeout, so
  a timed-out call can stop, and its answer and the settle both carry
  `pageErrors` — the uncaught throws, unawaited rejections and dead reactions
  that no notification raised
- `docs` answers a search, naming the page and section to read next, and says
  when the bundled docs belong to a different app version than the one driven;
  and `open` given a bare genome name answers with the hosted config's URL
  rather than a relative-path error
- a `jb` helper that several open views could answer throws naming them rather
  than taking the first, `jb.view()` is the finder with the same rule,
  `jb.getFeatures` reads on the worker the track already uses, and
  `session.layoutViews` arranges the open views
- a view's `exportSvg` returns its markup and takes `save: false`, so an agent
  can save a vector figure where it chooses on the linear, circular, dotplot,
  linear synteny and breakpoint split views
- JBrowse Web announces `window.jb` to a browser agent through `jb.help`, a
  console pointer at boot and a meta tag

  canvas displays, with sizing knobs and a `heightMode` modifier
  (`heightMode:fit:200`) beside it

#### Hosted configs

- `--hub`, to pull a hosted config from genomes.jbrowse.org
- friendly `--track` matching for hosted trackIds
- navigate `--loc` by gene name, via the hub's text-search index
- a `list` subcommand, to discover the hubs and their tracks

#### Output

- a compact LGV header and ruler layout
- a consistent export font, defaulting to a serif, with a Font dropdown in the
  export dialog
- a rendered figure for every README command that can produce one
- a batch-only flag used outside `batch` warns instead of doing nothing, a hub
  is fetched once for a whole batch, and the PNG conversion is piped rather than
  written through a temporary file

### @jbrowse/capture

A new product, whose readiness waits the website's figure pipeline shares: a
Puppeteer harness that drives a live JBrowse instance and screenshots it once it
has actually finished rendering.

- knowing when a genome browser is done is the whole problem, and every
  readiness signal JBrowse published was negative — no loading overlay, no
  display in its loading phase, no unpainted canvas — all of which pass on a
  page whose JavaScript has not started yet. The app publishes one positive
  selector now, saying it has finished
- a timeout names each unpainted display and the phase it is stuck in, rather
  than failing with a picture of an empty browser
- `--hub` names an assembly on genomes.jbrowse.org and `--loc` takes a gene
  name, since those configs ship a text index
- the readiness gate reads the census the app publishes beside that marker, so
  the wait is one selector and is satisfiable before the session object exists
- a `--session` naming synteny tracks contributes them to the gate, and a run
  told to expect no session still keeps one

### Website and documentation

The site was rebuilt on Astro, and its figures are generated rather than taken.

#### Tutorials

- 63 tutorials, each on real published data and following a practical workflow —
  cancer SVs, pangenome graphs, ChromHMM, TCGA cohorts, single-cell pseudobulk,
  QTL mapping, differential transcript usage, read-pair contact maps — with a
  hub page linked from the homepage and the nav bar
- a tutorial's opted-in command blocks are checked against its own build script,
  so a tool or flag the page shows is one the script uses, and a page that shows
  no command is ratcheted rather than left alone
- config blocks carry Config↔CLI tabs, checked to round-trip

#### Figures and tours

- every web figure is produced by a screenshot spec on the same readiness waits
  as @jbrowse/capture, so it is regenerated rather than going out of date, and
  its bytes live in S3 behind a lockfile rather than in the repository
- callouts anchor to the view model — a locus, a dotplot cell, a graph node —
  rather than to measured pixels, so a re-frame carries them with it
- a "Make this view yourself" recipe on every figure: the click path written for
  the reader's own file, a `jbrowse://` link that opens it in Desktop, the
  session spec JSON, an anywidget snippet, a CLI tab emitting `add-track` and
  `add-track-json` for a config.json, and an agent panel
- spec-driven video tours filmed the same way, each with a caption track, a
  reserved box, a poster and a link to the session it was filmed in, and a jump
  bar under the page's h1 linking the clips a reader came for — a `<video>`
  being a black rectangle in the scrollbar
- a web-based review UI for the corpus, with an onion slider, live links, and a
  whole-corpus diff ranked by how much a change explains it

#### The site

- Astro, in place of Docusaurus
- raw markdown for every page — `llms.txt`, a copy-markdown button and
  `/docs/<slug>.md`
- a docs sidebar with section headings, a filter, remembered open categories and
  breadcrumbs, and a table of contents on the long pages
- a site-wide image lightbox, syntax-highlighted code blocks, and automatic
  cross-links between the guides and the generated reference docs
- generated reference: the config pages are checked against the runtime slot
  manifest, and the state-model member pages are partitioned by doc value with
  anchor-linked inherited members
- footnotes, an RSS feed, and a release announcement that goes out to Bluesky,
  Mastodon and the newsletter
- a config block renders a JBrowse Desktop tab beside the config-file and CLI
  ones, derived from the same JSON, so a Desktop reader has a route to it
- a video embed reserves a strip for its control bar, dims again when the clip
  ends, and collapses a multi-video jump bar to a count
