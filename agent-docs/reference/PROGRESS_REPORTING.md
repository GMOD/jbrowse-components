# Status / progress reporting

How loading status travels from workers to the loading UI: one out-of-band channel,
orthogonal to the render lifecycle. Read it when touching a progress bar, a download
adapter, or a worker loop that should report progress.

## The one channel

`statusCallback: (status: RpcStatus) => void` (`packages/core/src/util/progress.ts`):

```ts
RpcStatus =
  | string
  | { message; current; total; source? }
  | { message; source }
  | { message; failed: true }
```

- A plain string is an indeterminate phase label.
- `{message, current, total}` adds a determinate fraction, unit-agnostic (bytes,
  blocks, records). The UI decides presentation; never bake percentages into the
  message.
- `{message, source}` is a phase label naming what it waits on (`source` is the URL in
  flight); it votes in the aggregate as the bare string it replaces.
- `{message, failed: true}` is a **retire that says the phase did not finish**,
  written only by the `finally` of `updateStatus` / `withProgress` / `downloadStatus`.
  Its `message` is the retire's usual string, so `statusMessageText` and
  `statusFraction` need no branch. It buys credit: `aggregateStatus` charges a
  completed phase its `total` and a failed one only the `current` it reached (ADR-087).
  The first aggregate it reaches consumes it.

Read `current`/`total` through `statusReading(status)`, which is `undefined` for a bare
label and a failed retire. There is **no** second `onProgress` channel; emit through
`statusCallback` only.

```
worker adapter → opts.statusCallback(status)
  → RPC drivers special-case statusCallback as out-of-band
    (message type `unknown`, so the object survives serialization)
  → the display's status callback thins the stream (its StatusWindow)
  → setStatusMessage splits it into statusMessage + statusProgress
  → DisplayLoadingOverlay draws a determinate bar + cancel, else a spinner
```

## No callback is a value, and it travels

A caller passing no `statusCallback` asks for no reporting, and every layer has a
branch for it: `downloadStatus` hands the reader no `onProgress`,
`createProgressReporter` skips its emit, `openPhase` allocates no stack. **A no-op
callback is not the same thing**: it is truthy at all three, turning those branches off
while looking like a tidy-up. `no-restricted-syntax` rejects `statusCallback = () => {}`
in a destructuring; keep the type `StatusCallback | undefined` and call
`statusCallback?.(…)`.

**This is not a speed argument.** The `onProgress` reader path (generic-filehandle2's
`toBytesWithProgress`, a `getReader` loop) is *faster* below ~10MB and only ~1.1× slower
past ~25MB in a Chrome worker:

What withholding the callback buys is that a caller who asked for nothing gets nothing:
no postMessage per status to a listener that drops it, and the two RPC drivers answer
the question the same way. `WebWorkerHandle.call` mints a `message-<n>` channel only
when there is a callback to feed, and `wrapForRpc` adds no key without one (as
`MainThreadRpcDriver` does). The tell that a layer re-manufactured one: a whole-file
download whose caller reports nothing still runs `toBytesWithProgress`.

## Helpers (`progress.ts`)

- `downloadStatus(label, cb, fn(onProgress))` wraps every download adapter: label +
  clear + a byte-reporter adapting generic-filehandle2 / tabix / bam / cram. `total` is
  optional (unknown Content-Length means indeterminate). Prefer it to `updateStatus`
  whenever the reader accepts `onProgress`.
- `createProgressReporter` / `withProgress` for determinate worker CPU loops.
  `report()` auto-increments, reads the signal and time-gates the emit, so calling it
  every iteration is cheap. It never yields, so a loop that can run for seconds takes
  `createAbortBreakpoint` beside it (NETWORK_ABORT.md §"Where a worker sees the abort").
- `updateStatus` for indeterminate phases.
- **Both phase helpers nest**: an inner phase restores its caller's label rather than
  blanking it, and `''` closes only the outermost. Two phases sharing one callback
  concurrently is fine; each retires its own entry.
- `statusMessageText` / `statusFraction` / `statusProgressLabel` extract the parts.
- `createStatusFanOut(cb)` merges concurrent statuses into one bar: each `slot()` is a
  `StatusCallback` remembering its own value and finished phases, and every write
  re-derives the shared status from all slots. The arithmetic is `aggregateStatus`
  (ADR-072: what it sums; ADR-080: how the phase is picked).

`parseLineByLine` (flat-file adapters) and `fetchAndMaybeUnzip`
(bigwig/bigbed/hic/sequence) forward determinate progress through these.

## Where a status lands: two fields, or one channel

A display declares `statusMessage` / `statusProgress` / `setStatusMessage` itself,
because half the display API reads them and ADR-041 is why `BaseDisplay` and
`FetchMixin` keep their own copies. A *view* with one operation to narrate holds a
`createStatusChannel()` in one volatile instead (the same split behind
`{ message, fraction }`; a plain function, not a mixin, per ADR-041).
`createAbortRotation(self, report)` takes the reporter as an argument because where the
status lands is the caller's decision (a display passes itself; the breakpoint split
view passes `self.fetchStatus`). `ProgressChip` takes the pair as one `status` object.

## The assembly load has its own status field

The per-display channel opens only once tracks fetch. Before that, `assembly.loadPre`
fetches four independent files at once (sequence index, chromAlias, cytoband,
genetic-code sidecar) through one `createStatusFanOut` slot per file (last-writer-wins
would blank the label when the fastest finished), behind one sink off the load's own
`StatusWindow`, writing `assembly.statusMessage` / `assembly.statusProgress`.

- **The guard.** `Promise.all` rejects on the FIRST failure while the other three keep
  downloading and reporting, repainting the field `loadPre`'s `finally` already cleared
  (a failed load under a live "Downloading cytobands 40%"). The `finally` closes the
  guard, then clears through `throttle.runNow`.
- Views read it through `assemblyManager.loadingAssembly(names)` (the first name not
  `initialized`) and expose `loading`, label, fraction and source for
  `ViewLoadingScreen`. Five views do: LGV, dotplot, linear synteny, circular,
  breakpoint-split. Which names to ask about is the only per-view part: `init` names
  assemblies before the view has materialized what `assemblyNames` derives from (LGV
  `initAssembly`; circular `init.assembly`; dotplot and synteny map `init.views`;
  breakpoint-split delegates to the first uninitialized sub-view).
- **`viewLoading` takes the assembly as a thunk, and the laziness is load-bearing**
  (same rule as `displayPhase`'s thunk): eager resolution asks the assembly manager on
  every read. `viewStatus.test.ts` and `CircularView.test.tsx` hold it.
- `ViewLoadingScreen` exists because a bare `LoadingProgress` renders an unconstrained
  full-width bar; its metrics match `DiagonalizeLoadingScreen`. It says only "Loading"
  for its first two seconds (`useSlowLoad`), as does the embed's `ViewStatus`, so a fast
  load does not flash "Downloading chromosome sizes".
- These adapters run on the **main thread** (`assemblyAdapters.ts`), so `statusCallback`
  is a plain call, still the `BaseOptions` one.
- **Labels name the data, not the file** (`Downloading alignments`, not the BAM or its
  index). chrom.sizes, `.fai` and the 2bit header are three sources for one answer, so
  all say `Downloading chromosome sizes`. Other labels: `Downloading chromosome
  aliases`, `Downloading cytobands`, `Downloading genetic codes`, `Downloading
  sequence`. Whole-file text reads are determinate through `fetchAndMaybeUnzipText`
  (which takes an optional `label`, and means those files may be gzipped); `.fai` and
  2bit readers (`@gmod/indexedfasta`, `@gmod/twobit`) expose no byte callback and get an
  `updateStatus` phase label.
- jbrowse-web's pre-`pluginManager` full-page spinner
  (`products/jbrowse-web/src/components/Loading.tsx`) reports no phases.

## Shared setup reports to whoever is waiting

An adapter that parses a whole file caches the work in one promise; hand-memoizing it
captures the *first* caller's `opts`, so once that fetch is superseded the replacement
awaits the same promise in silence behind a blank overlay. `createSharedSetup(run)`
(`packages/core/src/util/cachedSetup.ts`) fans progress out to the live waiter set and
clears the memo on failure. It **drops `signal` on purpose**: honoring one caller's
cancel would abort a parse the replacement is waiting on. Cancellation belongs to
per-call work (indexed range queries).

## Concurrent fetches share one field: aggregate, don't clobber

A fetch generation can fan out into N parallel per-region RPCs writing one field. The
answer on both sides of the RPC boundary is **`createStatusFanOut`, a slot per
operation**. One level up, concurrent *operations* sharing an owner's field aggregate
too (ADR-081): a display's viewport fetch, a lent `createAbortRotation` and a clustering
run each take a slot and none can end another's label. Which holds the label is
ADR-072's rule: the phase the owner reached first wins and the rest are charged below it.

On the main thread, `fanOutStatus(ctx, n)` (`@jbrowse/core/util/fetchContext`) owns it:
it returns N copies of a `FetchContext`, each `statusCallback` its own slot, so a caller
writes `statusCallback: ctx.statusCallback` and is right in a fan-out and in a batched
call (`callRpc` rebinds `this` to the copy). It sits in core because both fetch families
fan out inside one run: `callEachRegion` / `fetchEachRegion`, a `run` under
`installFetch` (multi-way synteny's N lanes, the breakpoint split view's N matched
tracks). **A VIEW's fetch rebuilds each slot as a context on its track**, since
`rpcSessionId` is `BaseTrackModel`'s (`makeFetchContext` says more). In the worker and
hand-rolled main-thread fan-outs (`BaseFeatureDataAdapter`'s multi-region `merge`, a
`Promise.all` over sidecars, MAF's two branches), call `createStatusFanOut` yourself.
The tell of a missing fan-out: the first operation to finish writes the `''` and the
label blanks while the rest still run.

This replaced a second implementation on the model (`regionStatuses` +
`setRegionStatus` + `makeRegionStatusCallback`) that retired on `undefined`, which
nothing sent, so finished regions stayed in the aggregate and the bar ran backwards.

## The stream is throttled on the callback, never on the write

An adapter emits ~40 progress/s and each write repaints the overlay and repositions its
Popper. `createStatusWindow(write)` (`@jbrowse/core/util`) is the one window (100ms),
leading **and trailing**: a leading-only gate drops the last write of a burst and froze
a bar at a boundary percentage. The trailing write fires on a timer, so its guard is
re-read inside the throttled body (`window.open({isCurrent})`); nothing else builds a
status callback by hand. **One window per owner**; streams come off it, so N parallel
region fetches thin to one flow.

`open` returns `{statusCallback, clear}`: **an operation retiring its own slot when its
work ends is what ends the stream** (a fan-out cannot see a batch end; ADR-080). Call
`clear()` in the operation's `finally`; it blanks the field only when no other operation
is reporting (ADR-081). A superseded rotation run needs none: the `begin()` that
replaced it retires its slot, since its own `finally` waits on work that may ignore the
abort. The window takes the field's single writer at creation, so whatever guards it
(`isAlive(self)`, a React `alive` flag) guards every status and clear. It reopens when
the field goes idle; `window.reset()` is for teardown.

Owners (so cadence is uniform): `createAbortRotation` (every latest-wins fetch: LGV
displays through `FetchMixin.runFetch`, which lends its window; dotplot, synteny,
multi-sample-variant sources, breakpoint split overlay features hold one directly),
`withDiagonalizeProgress` / `DiagonalizeDialog`, `useFetch` (one per effect run),
`assembly.loadPre`, `useMateDiscovery`, `useClusterRun`. Operations taking a *slot* on a
display's window: `runFetch`, `setupRunClusteringAutorun`, and a lent
`createAbortRotation` (ADR-081). This list is names, not a count, per
[ARCHITECTURAL_LIMITS.md](ARCHITECTURAL_LIMITS.md) "ordering is the contract".

- **`setStatusMessage` itself is never throttled**: hand-written phase labels are
  distinct and a trailing edge guarantees only the last of a burst.
- **The `''` a phase helper closes with IS throttled; the operation's `clear` is not**
  (ADR-071 turns on this). The `''` goes through the stream, so a phase that opens and
  closes inside one window paints nothing and still displaces the percentage queued behind
  it; it never *reaches* the field (an idle aggregate writes the last label alone).
  `clear()` is the operation's last word, which must *land* and reopens the window.
- **Hold the last determinate reading only where slots are raw reporters.**
  `createStatusFanOut` does; `createStatusWindow` does not, since a slot fed by another
  aggregate already had ADR-080's hold applied and re-applying it restores a percentage
  the child retired (ADR-071). `createStatusAggregate` takes it as a flag.

## A silent `rpcManager.call` is a lint error

`RpcHandles` must stay optional on `RpcCallArgs` (plugin ABI,
[PLUGIN_ABI_STABILITY.md](PLUGIN_ABI_STABILITY.md)), so two `no-restricted-syntax`
selectors in `eslint.config.mjs` reject an `rpcManager.call` object-literal payload
declaring no `statusCallback`, and the same for `signal`. Many calls should report
nothing; the rule makes that a **stated** decision (disable the line and say why). Grep
the disables for the accepted reasons: the work is narrated by the fetch it shares; there
is nothing to narrate or save; or the handles belong on an **interface** that does not
declare them yet (the disable names a `TODO.md` entry; that kind is worth fixing). A
spread payload is accepted as forwarding. Source only.

## A fetcher that declares no parameters is opted out, silently

`useFetch` hands its fetcher the key elements, then a **signal and status callback**
positionally. A function declaring fewer parameters type-checks and never sees either, so
`() => rpcManager.call(...)` gives a bare spinner over an uninterruptible read.

- **Declare the argument in the contract a display fills in**:
  `ClusterDialogProps.fetchMatrix` takes `{ signal, statusCallback }` like its sibling
  `run`.
- **A variable-length `useFetch` key makes trailing arguments unnameable.** Nest the
  caller's key pieces (`['clusterMatrix', [...]]`) so arity is fixed; `useFetch`
  serializes the whole key, so caching is identical.

## Cancel is durable and retryable

- `cancelFetch()`: internal reset; bumps `fetchGeneration`, clears `fetchCanceled`.
- `cancelFetchByUser()`: the overlay button; sets durable `fetchCanceled`, no generation
  bump, so nothing restarts.

`fetchCanceled` is a blocking state like `error` / `regionTooLarge`:
`FetchVisibleRegions` early-returns on it, `ClearBlockingStateOnViewportChange` clears it
on pan/zoom, and `runFetch` start is the single un-cancel point. `reload()` is the retry
path. The comparative displays (also on `FetchMixin`, ADR-105) keep their cancel durable
until Retry with no clear-on-viewport-change; see
[SHARED_CANVAS_VIEWS.md](SHARED_CANVAS_VIEWS.md).

## Test coverage trap

Desktop text-indexing progress (`indexDriver` → `indexJobsModel` → job card) is covered a
hop at a time (`indexJobsModel.test.ts`, `CurrentJobCard.test.tsx`,
`jbrowse-web/browser-tests/suites/jobs-list-progress.ts`). The hop nobody covered kept
breaking: the card's determinate branch (the `color-mix()` track and indeterminate
keyframe sweep exist only in a real browser) was repaired three times before anything
rendered it. The ixIxx tail is unmeasured, so the bar goes indeterminate after the
record stream's `'end'` rather than sitting at 100%.
