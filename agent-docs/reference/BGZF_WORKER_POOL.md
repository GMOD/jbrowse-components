`CramAdapter` is absent on purpose: its codec pool is a different pool.
`Gff3TabixAdapter` and `GtfTabixAdapter` are absent on purpose too. GFF text
inflates ~18x, and reassembling it is serial work on the calling thread that no
worker count reaches, so the library measures it at or below parity
(`@gmod/bgzf-filehandle` docs/worker-pool.md).

## Behavior

- **No workers start until a chunk of at least `POOL_MIN_DECOMPRESSED_BYTES`
  inflated bytes arrives.** Smaller chunks inflate on the calling thread, where
  the round trip outweighs the gain. A fixture of only small chunks measures
  nothing, silently.
- **No read waits on a worker.** While workers boot, reads inflate in process. A
  worker that raises `error` or sends an undeserializable reply turns the pool
  off for good, and its in-flight request returns to the calling thread. A
  worker that never starts is left alone and adopted if it starts later. Capping
  Firefox's `dom.workers.maxPerDomain` at 4 reproduces the old hang on a volvox
  GFF3 tabix track.
- **BAM gets about 1.95x; tabix gets less.** Quoting the BAM figure for a VCF
  track overstates it by a third.

## What tabix is worth

Fixture `1kg.chr1.subset.vcf.gz` from tabix-js test data: 213MB of 1000 Genomes
over `chr1:10,109-622,047`, thousands of samples, ~60KB lines. Headless Chrome,
real HTTP with range requests, 4 workers, arms interleaved, min of 6, both arms
asserted to return the same record count.

So **1.34-1.46x<!--m:bgzf-pool-tabix.speedup.range--> on a big multi-sample
VCF**.

Why tabix gets less than BAM: about 28% of a cold VCF query is per-line byte
scanning and string decoding, not decompression. A second pan over the same file
answers from the decompressed chunk cache and isolates it. The decompression
itself moves 1.83x; the scan floor drags the end-to-end figure to 1.45x, which
Amdahl predicts (1.49x). The floor is large for VCF because every line carries a
genotype per sample. Anyone wanting more than 1.5x on multi-sample VCF should
attack the scan, not the decompression.

## Verifying the pool engages

The failure mode is silence. jbrowse-web runs adapters inside a web worker, so
the pool is a worker spawning workers. Where nested workers are unavailable
(Safari before 16.4), `workersAvailable()` is false, the pool resolves to
`undefined`, every read inflates in process, and nothing fails. That graceful
degradation is what makes the option safe to pass unconditionally.

To re-check, count worker targets with puppeteer (`browser.on('targetcreated',
…)`, filter `blob:` URLs) while loading a session with one bgzip-backed track,
and run a non-bgzip control (a bigwig spawns zero) in the same session. Four
means engaged, zero means fell back. The view must read a chunk past the size
gate: the 1kg VCF does, volvox does not, so zero `blob:` workers on volvox is the
pool working.

**The four is per RPC worker, not per session.** `getSharedWorkerPool()`
memoizes per JS context, and `WebWorkerRpcDriver` gives each track a sticky
worker out of `clamp(hardwareConcurrency - 1, 1, 5)`, so pool workers multiply
by the number of contexts. Each has its own grow-only wasm heap; the pool
terminates its own workers after an idle period and respawns on the next call,
which is transparent to holders in a way `destroySharedWorkerPool` is not (a
destroyed pool throws out of `decompressBlocks`).
[BAM_STACK_INTEGRATION.md](BAM_STACK_INTEGRATION.md) § "Seam 1" owns the counts.

`products/jbrowse-web/browser-tests/percontext-probe.ts` is the harness. It needs
a recursive `Target.setAutoAttach`, since a pool worker is a worker inside a
worker and `memHelpers`' one-level tracking sees only the RPC workers. Run it
with `TRACKS` above the RPC pool size to separate "per track" from "per
context".

## Benchmark traps

[BENCHMARKING.md](BENCHMARKING.md) holds the general rules. The ones specific to
this pool:

- **Six rounds minimum.** The HTTP cache warms for several rounds, and a min over
  the unplateaued series once read the pool as a 0.74x slowdown.
- **Node cannot measure it, and this doc owns that trap.** `getSharedWorkerPool()`
  needs a global `Worker` plus Blob URLs, so it resolves to `undefined`, the
  in-process path runs and every node bench reports parity. The same holds for
  any worker-shaped question. `packages/core/src/util/bgzfWorkerPool.test.ts`
  pins the property.
- **Jest suite time is not a signal for import weight.** The helper imports
  dynamically so the inlined worker blob stays out of the initial bundle. A
  claimed jest-time win for that did not reproduce; it was a cold transform
  cache in a fresh worktree.

Not committed. Esbuild a browser entry importing `TabixIndexedFile` and
