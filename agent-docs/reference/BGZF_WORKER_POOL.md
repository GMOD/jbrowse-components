`sharedBgzfWorkerPool()` (`packages/core/src/util/bgzfWorkerPool.ts`) spreads
BGZF block inflation across up to four workers instead of the thread that asked.

`CramAdapter` is absent on purpose: its codec pool is a different pool.
`Gff3TabixAdapter` and `GtfTabixAdapter` are absent on purpose too. GFF text
inflates ~18x, and reassembling it is serial work on the calling thread that no
worker count reaches, so the library measures it at or below parity
(`@gmod/bgzf-filehandle` docs/worker-pool.md).

## Behavior

- **No workers start until a chunk of at least `POOL_MIN_DECOMPRESSED_BYTES`
  inflated bytes arrives.** A fixture of only small chunks measures nothing,
  silently: volvox never engages the pool.
- **No read waits on a worker.** A worker that errors turns the pool off for
  good and its in-flight request returns to the calling thread; a worker that
  never starts is adopted if it starts later. Capping Firefox's
  `dom.workers.maxPerDomain` at 4 reproduces the old hang on a volvox GFF3 tabix
  track.
- **BAM gets about 1.95x; tabix gets less.** Quoting the BAM figure for a VCF
  track overstates it by a third.

So **1.34-1.46x<!--m:bgzf-pool-tabix.speedup.range--> on a big multi-sample
VCF**. The slice is 213 MB of 1000 Genomes over `chr1`. A second pan over the same
file answers from the decompressed chunk cache and so measures the halves apart:
the line scan is 28% of the cold query and the pool reaches the rest at 1.83x, so
Amdahl's law gives 1.49x against 1.45x measured. That 28% is byte scanning on
enormous per-sample lines, so passing 1.5x on multi-sample VCF means attacking the
scan, not the inflate.

Tabix gets less than BAM because a large share of a cold VCF query is per-line
byte scanning and string decoding, not decompression; every line carries a
genotype per sample. Anyone wanting more on multi-sample VCF should attack the
scan, not the decompression.

## Verifying the pool engages

The failure mode is silence. jbrowse-web runs adapters inside a web worker, so
the pool is a worker spawning workers. Where nested workers are unavailable
(Safari before 16.4), `workersAvailable()` is false, every read inflates in
process, and nothing fails. To re-check, count `blob:` worker targets with
puppeteer (`browser.on('targetcreated', ...)`) on a session with one
bgzip-backed track plus a non-bgzip control; zero `blob:` workers on volvox is
the pool working.

**The four is per RPC worker, not per session.** `getSharedWorkerPool()`
memoizes per JS context, so pool workers multiply by the number of RPC
contexts. The pool terminates its own workers when idle; `destroySharedWorkerPool`
makes `decompressBlocks` throw. [BAM_STACK_INTEGRATION.md](BAM_STACK_INTEGRATION.md)
§ "Seam 1" owns the counts.
`products/jbrowse-web/browser-tests/percontext-probe.ts` is the harness; it
needs a recursive `Target.setAutoAttach`.

## Benchmark traps

[BENCHMARKING.md](BENCHMARKING.md) holds the general rules. The ones specific to
this pool:

- **Six rounds minimum.** The HTTP cache warms for several rounds; a min over
  the unplateaued series read the pool as a 0.74x slowdown.
- **Node cannot measure it, and this doc owns that trap.** `getSharedWorkerPool()`
  needs a global `Worker` plus Blob URLs, so it resolves to `undefined`, the
  in-process path runs and every node bench reports parity. The same holds for
  any worker-shaped question. `packages/core/src/util/bgzfWorkerPool.test.ts`
  pins the property.
