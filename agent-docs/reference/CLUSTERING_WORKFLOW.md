# In-App Clustering Workflow

`plugins/wiggle`, `plugins/variants`, `plugins/marks` and `plugins/maf` run a
cluster dialog that sends an RPC (`MultiWiggleClusterScoreMatrix`,
`MarkClusterRows`, `MultiSampleVariantClusterGenotypeMatrix`). The RPC builds a
feature matrix and runs `@gmod/hclust`; the dialog commits `{ order, tree }`
through `applyClusterRun`, which calls `model.setRowOrder(rows, { tree,
provenance })`. The Manual tab's pasted order lands through
`clusteredCladeLayout`, the step a run ends with. Every family composes
`TreeSidebarMixin` (`packages/tree-sidebar`), which stores the arrangement in the
display's `rows` config object (ADR-157) and derives `clusterableSources`; the
mixin's rules are in [TREE_SIDEBAR](TREE_SIDEBAR.md).

## Matrix construction

**Wiggle** (`getScoreMatrix.ts`): each column is the MEAN of every feature
covering it, because several features routinely land in one.

- **A column no feature covers is NaN**, imputed to the column's mean before
  hclust and written `NA` to the TSV and R script, as a no-call is; the script
  imputes the same way before `dist`, so both orders agree. Reading it as 0 put
  a bedMethyl sample missing coverage beside the unmethylated ones. A bedGraph
  that omits its zero runs loses those zeros to the mean, the cost of one rule
  for every file.
- **On a log or symlog axis the scores are placed through the display's scale**
  (`MatrixScale`), so rows cluster on the heights drawn and the caption names
  the scale. Linear sends none: an affine map moves no average-linkage merge.

**The accumulator is `Float64Array` and the row is `Float32Array`, deliberately.**
Summing many f32s into an f32 is uncompensated; the row stays f32 because it is
a `postMessage` transferable and BigWig scores are f32. `getScoreMatrix.test.ts`
pins the width with a 2e7 outlier among a hundred 1s.

**Variants** (`getGenotypeMatrix.ts`): a multiallelic site is several columns;
values are diploid-scale dosage with `NaN` for a no-call
(`genotypeMatrixEncoding.ts` says why). hclust rejects non-finite input, so the
in-app path runs `imputeMissingToSiteMean` first; the R/TSV export writes `NA`
and the R script imputes it the same way. Phased mode gives one row per
haplotype. The dialog commits through one `applyOrder(order, matrixRowNames)`
callback, so phased and unphased paths commit identically.

## Staleness has one imperative half and one derived half

`clusterLayout` positions leaves positionally (leaf `i` on row `i`), so a tree
that no longer names the rows on screen draws against the wrong ones. The
mixin-side rules are in
[TREE_SIDEBAR](TREE_SIDEBAR.md#does-the-tree-describe-these-rows-is-derived-not-remembered).

- **`setRowOrder` → `rowOrderWillDropTree`** covers writes that go through it,
  so every action that moves rows routes through `setRowOrder`.
- **`computeClusterHierarchy`** takes the drawn rows and returns `undefined`
  unless the tree's leaves are exactly those names in that order. It backstops
  rows that move with no order write (a `sources` decoration, a discovered row
  set growing, phased expansion switching on).

The focus (`rows.kept`) is matched by name without a tree, so a reorder keeps it
on purpose; only a change to what rows are called invalidates it.

A guide tree an adapter supplies (`guideTreeNewick`, MAF's `.nh`) is data, not
config: `rowTree` draws it and never writes it to `rows.tree`.

Row order is not a fetch input (FETCH_KEYS.md, "Row order is not a fetch
input"), so tree and layout land together. A "wait for the other half" mechanism
that outlives its asynchrony does not fail loudly, it never fires;
`plugins/variants/src/LinearVariantDisplay/clusterTreeLands.test.ts` guards this.

Helpers live in `packages/tree-sidebar/src/clusterUtils.ts`.

## Performance regimes

At default filters a population panel is thousands to tens of thousands of
columns wide, so the Euclidean distance build dominates, not hclust's merge loop.
`clusterMatrix` tries `gpuDistanceMatrix` first
(`packages/tree-sidebar/src/gpuDistanceMatrix.ts`) and falls back to wasm below
the work gate, without a WebGPU device, or when the dispatch fails validation or
reads back wrong. **A truncated dispatch raises no error and leaves zeros**,
which hclust would merge first at height 0, so `distanceSpotCheck.ts` recomputes
a few pairs in f64 and a mismatch throws.

**Ties make the merge loop the cost.** hclust rescans each cluster's cached
nearest neighbour when it merges away; on mostly identical rows every merge
invalidates every cache, and a distance kernel does not help.

**The hclust wasm heap is capped at `MAXIMUM_MEMORY=2GB`**: the N×V×4 input and
the N²×4 distance matrix share it. Nothing in this tree weighs N against V; the
dialog shows whatever `clusterMatrix` throws.

### The distance build, measured

`executeClusterGenotypeMatrix.ts` hands the tail one Float32 dosage row per
sample (one per haplotype in phased mode), with one column per site that passes
the MAF and missingness filters, whose defaults keep every site in the window.
On a 1000 Genomes window (2504 samples, 5008 haplotypes, chr22:20-21 Mb, 22,383
phased sites) hclust's merge loop is about 40 ms of a run that takes seconds to
minutes; the distance build is the rest.

Radeon Pro 5300M), hclust warm in node, GPU in headed system Chrome including
upload and readback:

- **The GPU's margin grows with N x V.** dog10k (167 dogs, 611 columns)
  clusters in 16 ms on the CPU and the dispatch takes 18 ms, so a small cohort
  stays under `MIN_WORK` (10^9 pair-elements) on the wasm.
- **The JS column is the pre-wasm baseline**, at the same shapes. The C port
  bought a steady 4 to 5x on the distance build; the rest of hclust's own 446x
  headline (`docs/optimizations.md` in that repo, benchmarked at V = 20) is
  merge-loop work that does not touch this build. 5.0.0's first call was 12.6 s
  on the first row; 5.1.0's is within 5% of warm, and its 2.5x came from doing
  differences and squares in f32x4 with the promotion to f64x2 every 16
  elements.
- **The kernel is a floor**: one thread per pair looping over V from global
  memory, no shared-memory tiling, chunked at 64 MB per upload. A tiled or a
  packed 2-bit popcount kernel (the LD kernels' shape) would go further.
- **Parity needs fractional input.** The kernel sums squares in blocks of 16
  under Kahan compensation. On the phase 3 matrices, integer dosages with no
  no-calls, it matches f64 exactly; dog10k's imputed values match to 1.2e-9
  relative. The variant path's dosages are not integers in general:
  `readAltDosages` writes `2 × calls / called`, and `imputeMissingToSiteMean`
  writes a site mean into every no-call (15% of sites, 0.7% of cells, on the
  hosted 3,202-sample 1KGP callset). Without the compensation an f32 sum drifts
  with V, 7.7e-7 relative at 512 columns to 3.6e-5 at 20,000, so `--fractional`
  on the probe is the check.
- **Handed distances, the wasm never sees the N×V input**, so the heap wall
  above is the fallback's. `clusterData({ distances })` (hclust 5.2.0) reads
  the upper triangle, the half the kernel writes.
- **WebGPU only, by construction.** Storage buffers have no GLSL ES 3.0 target
  ([GPU_HAL](GPU_HAL.md)), so the wasm path is not optional.
- **No shipped config reaches the large rows.** The hosted 1000 Genomes slice
  (`…HBB_5.2-5.3Mb.vcf.gz`, 2,504 samples, 3,984 sites) is the first row and
  ends at 100 kb. The 3,202-sample 1KGP SV callset on `jbrowse.org/demos/1000g`
  is ~70 sites per Mb and unphased, so its cost is the merge loop's tie
  rescans, which the kernel does not touch. The large rows are a user pointing
  the app at a full phase 3 chromosome, the public URL
  `test_data/1000g_snpeff_chr1/README.md` builds from.

`products/jbrowse-web/browser-tests/probe-gpu-distance-matrix.ts [N] [V]`
bundles the shipped `gpuDistanceMatrix` into headed Chrome (headless has no
WebGPU), runs it on a synthetic dosage matrix against an f64 reference, then
compares hclust's tree on the returned matrix with `clusterMatrix`'s on the
rows. `--matrix=<file.bin>` reads a dump from `pnpm bench:real --dump` in the
hclust repo, where the CPU columns come from;
`measurements/cluster-distance-gpu.json` is the record behind the table.

Spearman against the finest binning is already 0.965 at 512 columns, so the
broad grouping survives coarsening, while only 35% of adjacent row pairs do,
and 512 to 5000 columns costs about 105 ms; the cap is 5000.

**A GPU kernel does not move this.** At 464 rows the kernel runs 75 ms against
the wasm's 126 ms at V = 5000 and 252 ms against 560 ms at V = 20,000, 1.7x to
2.2x where the same probe gets 3.6x at N = 2504. 464² / 2 is 107k pairs, which
does not saturate a GPU or amortize the ~50 ms of fixed dispatch; at V = 512 the
kernel loses outright. The win is in N, and the MAF path does not have the N.

### Which in-browser compute is worth doing

The clustering workflow is analysis the app runs itself, which is the exception
the "just load it as a track" rule allows only when two tests pass:

- **The input is a runtime choice with a combinatorial domain.** No offline
  pipeline enumerates every window, sample subset and filter setting, so there
  is no track to load.
- **The work is superlinear in what is on screen.** A pairwise product over a
  viewport-sized input is where a GPU dispatch beats a worker; per-site
  statistics are linear and stay in the worker.

A feature failing the first belongs in a pipeline; one passing the first and
failing the second belongs in the worker, not a shader. Declined against them:
read x read grouping at a locus (WhatsHap does it properly and writes HP tags),
coverage and pileup on the GPU (linear, and a coverage GPU pass that compiled
clean cost correctness), per-site population statistics (linear; Fst between
user-chosen groups is a worker feature), genome-wide sequence search
(bandwidth-bound on fetching the FASTA), Hi-C balancing (elementwise, and files
ship normalization vectors) and a local LLM (fails the first test). The open
candidates are
[keep-the-sample-distance-matrix-resident](../ideas/waiting-on-a-call/keep-the-sample-distance-matrix-resident.md)
and [a-k-mer-dotplot-of-the-visible-windows](../ideas/waiting-on-a-call/a-k-mer-dotplot-of-the-visible-windows.md).
