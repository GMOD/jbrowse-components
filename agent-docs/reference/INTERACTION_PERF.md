# Interaction perf: which components re-render per frame

Interaction is main-thread-JS bound, not GPU- or MobX-bound. The cost is React
re-render plus the MUI/Emotion styling each render pays, so the one lever is
**fewer components re-rendering per frame**. The tax scales per track, since each
track mounts its own overlay and chrome subtree (`jb2bench/scripts/render/multibam.ts`
sweeps track count).

## Pool a list where the gesture changes every key

Attributing every DOM mutation during a 5x zoom to its nearest `data-testid`
subtree found the churn in the coordinate ruler. `ScalebarCoordinateLabels` keyed its
tick divs by base, which changes every key on a zoom, so React rebuilt the whole tick
set each frame. Positional keys make the list a pool:

Read the trade, not the total: structural churn is the expensive class, and the

`website/scripts/measure-zoom-churn.ts` reproduces it against

a feature's id, so `FloatingLabelsLayer` already pools, and positional keys there
would repaint every surviving label.

## An array-rebuilding computed re-renders every observer that reads it

- **A computed that rebuilds a fresh empty array is not free.** Return one shared
  frozen array (so MobX's `===` stops) and `null` from the component. A census arm
  starting at offset 0 never sees this; the mid-contig arm exists for it.
- **Clamp inside the computed.** `visibleRegions` rebuilds fresh objects every
  frame; the view's `contentRightEdgePx` applies `Math.min(trackWidthPx, …)` where
  MobX can stop at it. Publishing the raw edge changes nothing.
- **Split a computed by the clock each half answers to.** `sashimiJunctionSections`
  is the memoized merge and `projectSashimiArcs` was the per-frame half, until
  the arcs became link marks and left the frame (ADR-222):

## Count the renders in jsdom before you profile a build

(`ZOOM_CENSUS=1` prints per-component tables). Two limits:

- **A count is a floor.** A child re-rendered by a parent's fresh props runs no
  reaction of its own, and `mobx` emits spy events only in its development build.
- **Only the view-geometry half is deterministic.** Ruler, scalebar and overlay
  counts repeat to the integer; anything downstream of a fetch races the wall
  clock. Quote per-component counts of the first group, not the gesture total.

## Profile the production build

Take render **counts** from a dev build and nothing else: React's dev
instrumentation inflates component cost unevenly and reorders the ranking.
`products/jbrowse-web/browser-tests/profile-zoom.ts` is the harness. Traps that
each produced a confident wrong answer:

- **Charging a message its enclosing task overstates it.** Sum the event's own
  `dur`, not its `RunTask`'s.
- **`page.mouse.wheel` measures the wrong thing.** Each call is a CDP round trip
  the page's busyness delays, so a slower build runs a shorter gesture. Drive
  wheels from inside the page on a wall-clock schedule and bound the sweep by
  `bpPerPx`; two arms over different `bpPerPx` ranges are not comparable.
`zoom-token-churn` builds each arm twice from identical source, so the spread
between those builds is the `floor` column. A delta that does not clear its own
floor says nothing.

### Any canvas text op flushes the document's style

Setting `ctx.font` **or** calling `ctx.fillText` resolves the canvas element's
computed font, which flushes the whole document's pending style recalc;
`fillRect` does not. **An overlay that draws text must gate the text work on
something actually being drawn** — caching `ctx.font` does not help, since
`fillText` pays the same flush. Quote the `bpPerPx` range with the number.
