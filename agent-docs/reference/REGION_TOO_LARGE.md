# The region-too-large gate

A gated display's worker asks the adapter's index for a region's byte size
before downloading. Over budget refuses and shows the "region too large"
banner; canvas adds a feature-density axis on the same banner. Force-load turns
both off for the track.

![What one gated fetch decides, and what the first refusal does to the batch](diagrams/region-too-large-gate.svg)

## How the verdict is built

**Neither budget is an RPC cache key.** `resolvedByteLimit()` and the feature display's
`maxFeatureDensity` travel as call-site arguments, never in `rpcProps()`, where
a swing at 20 kb or on force-load would be a full refetch. Raising a budget
refetches the refused region; lowering one re-banners from the stored
measurement with no RPC.

**The first refusal ends the batch and leaves the fetch running to its end.**
`refusalScope` aborts the siblings on a signal of the fan-out's own and stops
waiting for them, so the fetch ends the ordinary way with the verdict and its
viewport stamp already committed, and the plan's next run declines on them.
A linear display issues no separate estimate RPC. `CoreGetRegionByteEstimate` serves the track
export, `jb.getFeatures`, and the circle's chord variant display, whose
`CoreGetFeatures` takes no budget (`installChordFetch`).

## Measurement follows the viewport

The verdict is the last measurement, and the fetch always takes the next one.
Ungated, every fetch measures before it downloads. Gated, the fetch skeletons
skip only on `gateSkipsMeasuredViewport` — the banner is up *and* the
measurement already describes the viewport on screen — so a blocked display
runs one fetch per settled viewport that stops at the gate. Skipping
unconditionally freezes the estimate; never skipping spins on the
`fetchGeneration` bump.

**The density budget counts top-level features per pixel.**
`LinearBasicDisplay` defaults to 10, so a whole bacterial genome draws (E. coli
K-12's 4,751 top-level features over 4.6 Mb are 3.2/px at 1,500 px); the
variant display's records band keeps 1 (ADR-037). At 10, human RefSeq GFF3 at
whole-chromosome zoom passes the density axis (table below) and only the byte
gate refuses it: chr1 is 5.5 MB by the index, over `fetchSizeLimit`'s 5 MB,
while chr10 and chr17 are 2.8 MB and draw.

`calculateFeatureDensityStats` (`stats.ts`) grows a window from a point 25% into
the region. `densityProbeGate` can stop it once an *admitted* count reads
`DENSITY_SETTLE_MARGIN` times over budget; growth still tests the raw count, so
a filtered view is not refused on a population it filters away. A budget that
cannot size a window (`0`, NaN from jexl) yields no gate. One window is one draw
from a clumpy distribution:

## The sub-floor budget tier

`SUB_FLOOR_BYTE_BUDGET_FACTOR`. An off-switch would be bypassable, since a
region over budget below the floor was over budget at the floor too; but the
estimate stops moving below a BAI's 16 kb bins, so the banner's advice is
unactionable:

**Alignments keep the doubled budget; a wider one and an off-switch were both
tried on 2026-11-22 and declined.** Index bytes do not rank loads across index
kinds: the 50,000x BAM's 2 kb window estimates 112.4 MB and drew in 4.9 s on
0.9 GB of worker heap, while the same depth's CRAM estimates 108.4 MB for the
whole genome, the 18 s and 3 GB row that lost a renderer in one run of six. No
single budget applied to both windows alike passes the first and stops the
second.

- **A fetch reads the screen plus half a screen each side**, so a view just
  under 20 kb fetches about 40 kb, the whole of a 30 kb genome. With no budget
  under the floor, one zoom-in from the whole-genome banner loaded it unasked;
  with a 120 MB one, a factor of 24 over the alignments adapters' 5 MB
  `fetchSizeLimit` default, the CRAM's 108.4 MB did the same.
- **With no budget nothing is measured**, so the stored estimate goes stale
  under the floor and re-banners on zoom-out for a place the view has left.
- **A factor multiplies a raised limit too**: that factor of 24 over this
  section's 60 MB is 1.44 GB.
- **A wider budget makes the banner's zoom advice wrong the other way**: two
  flat measurements above the floor drop "Zoom in to see features" while a
  view under it would load.

## A budget has a scope

`gateByteLimit` is what one **region** may cost, so a region set reduces by max
(`measureRegionBytes` worker-side, `commitFetchBytes` main-side) and a view
where every region fits is never refused for their sum.
`CoreGetRegionByteEstimate` takes a required `scope`: the save dialog asks
`wholeRequest`, because a save is one download, and so does the chord variant
display, because the circle holds every region's records at once.

## Shared primitives

**Hooks a display may override.** `gateEnabled` (a literal, checked by
`check-gated-adapter-budgets`); `densityTooLarge`; `byteGateAdapterPath`;
`byteGateAdapterConfig`. `FeatureGateMixin` composes after
`MultiRegionDisplayMixin()`; `no-restricted-syntax` fails the other order, whose
cost is a silently off gate.

**The budget.** `resolveByteLimit` prefers the adapter's declared
`fetchSizeLimit` at `byteGateAdapterPath` over the display's slot and doubles it
below the floor. Consumers read `resolvedByteLimit()`.
