# Handoff: Display Drift audit — fixes landed, and what is left

Source: a read-only audit ("Display Drift", 92 findings across 21 display types).
19 commits landed on `main` between `6550bf71b4` and `24f71afdf3`. Every fix was
verified against the code first, carries a regression test proven red without it,
and had its scoped suite run green. Six of the larger changes were then
adversarially cross-checked by a second agent; two of those reviews found real
defects, which are fixed and noted below.

**2. Two confirmed review findings, fixes not started.** Agents were dispatched
and stopped before editing anything.

*Arc* (`bd65f934c7`), four confirmed by repro:
- The `<= 0` half of the stroke fallback un-hides arcs the NaN bug never touched:
  a literal `thickness: 0` or `-4` now paints at 1px, so
  `jexl:...>5?3:0` no longer hides low-score arcs. Any fix must keep scoreless
  BED3/BED4 arcs visible — `logThickness` answering a visible default for an
  absent attribute, with the stroke fallback narrowed to non-finite, is the
  shape that keeps both.
- `finiteShape` flattening a zero-length feature's `-Infinity` height to 0 gives
  it `arcDistancePx === 0` instead of `Infinity`, so `hitTestArcs` returns a
  tooltip and click target for ink that strokes nothing. Culling zero-extent
  arcs may make `finiteShape` dead code — check before keeping both.
- `logThickness` does not answer 0 for a negative attribute as its comment says:
  `Number.isFinite` only catches `<= -1` (`-0.5 → -0.693`). It is a public jexl
  function users compose, and `website/docs/config_guides/jexl.md` (~line 129)
  still documents it as `log(attribute + 1)`, now wrong twice over.
- `plugins/arc/CLAUDE.md` claims a display cannot construct a `LaidOutArc`.
  TypeScript does not apply excess-property checking to an object literal
  returned from a callback, so a `toArc` returning `selected`/`xMin`/`xMax`
  typechecks clean under both compilers. Runtime is safe (spread order); the
  wording promises enforcement that does not exist.

*Wiggle score menu* (`d6547054d3`), two confirmed:
- The caption is correctly gated on `hasManualScoreBounds` but still prints the
  *resolved* pair, so with only one end set a GC content track reads
  `Set min/max score (0 – 0.75)...` where that `0` is `defaultScoreDomain[0]`,
  indistinguishable from a user-pinned 0. `manualMinScore ?? 'auto'` says it
  honestly; the `'auto'` spelling is already in that expression.
  `scoreMenuItems.test.ts` (~121) and `gcParamsInvalidate.test.ts` assert the
  misleading string.
- `SetMinMaxDialog.tsx` (~20-25) still hand-rolls both sentinel comparisons and
  its prop type cannot reach the new getters, so the commit's claim that the
  mixin "owns the sentinel comparison once per end" is not true of the tree.
  Routing it through them is a net deletion.

**3. Open finding, deliberately unfixed: the variants insertion legend still
recomputes per pan frame.** `insertionLegendColor` walks every loaded record and
re-renders `FloatingLegend` on every pan. The fix attempted in `72eb504835` was
reverted in `251ee1c67f` because a cross-check disproved it — see below. An
exact answer cannot be pan-stable, because the snap phase is `offsetPx`;
choosing between an exact per-frame legend and a stable approximate one is a
design decision, not a cleanup.

## What the cross-checks changed

`251ee1c67f` reverts the variants legend getter. The claim it rested on —
"`markersForBlock` culls nothing, so only `pxPerBp` and the snap phase come off
the block" — is true as stated, but the snap phase is load-bearing:
`snapCellEdgePx` differences round to `floor(d)` or `ceil(d)` depending on
`frac(screenStartPx - start * pxPerBp)`, which the painter takes live and the
synthetic block pinned at 0. Measured against the real model, the painter drew a
marker on 12 of 24 half-pixel pan positions where the legend showed none, and
the legend advertised one on 4 of 16 frames where the painter drew none.
Reachable on the long-REF-plus-longer-ALT pangenome shape `getInsertedBp` exists
for. Walking `perRegionCellMap` was a second regression: the swatch lit for a
displayed region scrolled entirely off screen.

`9d8f1637d6` corrects the MAF CDS strip. Capping at `h` was incomplete — `h`
itself floors at `MIN_DRAWN_ROW_PX` and overhangs its row below 1px — and at
`h <= 2` the cap made the strip the *whole* band, so on the 447-way shape it was
written for, every species with a CDS had its row replaced by the frame colour.
Capping at half the band holds at every row height. The old test asserted
`h <= 1.24` at `rowHeight: 1.24`, true only because 1.24 > 1; it would have
passed on a strip covering sixteen rows.

`023cff46fe` pins the `dataFill` flags. The refactor traded a lossy-but-automatic
derivation for seven hand-written flags, two of which (`mateRefName`,
`bisulfite`) were previously inherited — and deleting both left the whole plugin
green, because the test that gates on the flag reads it on both sides.

## Reviewed and found sound

Worth not re-litigating. The colour-scheme refactor was diffed old-vs-new over
718,848 cases: 96 disagreements, all on the two schemes it set out to fix. The
MAF cull collapse was proved exact at every boundary case across all ten sites,
and the codon variant it changed turned out to be an off-by-one fix, not a
loosening. The `PointerLayer` merge corrected the audit — three call sites
*did* depend on the observer difference. `clampToContig`'s pass-through was left
alone (deliberate and pinned) with the fix at the two callers that conflate two
answers. The two variants hit tests were deliberately not consolidated: they
share everything shareable and differ in pick strategy.

## Audit findings checked and rejected

"A promotable pin sits inside a permanently-disabled submenu" (ranked High). The
submenu is disabled only while `readConnections === 'off'`; enabling "Show read
arcs" in the same menu enables it, so `readConnectionsDown`'s session-wide
default is reachable. Tightening `pinnedSlots` to skip disabled submenus would
turn the coverage test red on a deliberately state-gated row.

## Late review (arrived after the above was written): three more changes sound

The PointerLayer merge, the clustering abort and the MAF conservation band were
all cross-checked and confirmed correct, with each new test proven to fail
against the pre-change source. Notably: React Compiler provably does not compile
`PointerLayer` (no `_c(` in the babel output), so the staling hazard that would
have made the merge silently wrong does not exist; the clustering disposer fires
on every real teardown path, and the worker genuinely unwinds within the
stop-token throttle; and no fourth raw `conservationHeight` read was missed
anywhere in `plugins/maf`.

Low-severity leftovers, none urgent:

- `MafConservationBand.tsx:63` now evaluates `conservationTicks(0)` when the
  band is off, producing an inverted zero-span axis at negative coordinates.
  Nothing renders it (every consumer is behind `show`), but
  `ticks={conservationBandActive ? conservationTicks(h) : undefined}` would
  state the invariant the code relies on.
- `stateModel.ts:998-1004`'s new docstring overstates the getter: in fit mode
  `statedBandBounds` returns undefined and `conservationDisplayHeight` equals the
  raw slot, so a config with `conservationHeight: 5000` and no `height` still
  yields a 5000px band. It is a reservation, not a bound.
- `runClusteringAutorun.test.ts` stubs `openStatusStream`, so the destroy-mid-run
  case never exercises the real stream's `clear()`. Safe by hand-check (the
  `isAlive` guard is one layer down in `writeStatus`), but the test cannot tell.
- `runClusteringAutorun.ts:104-108` runs `getContainingView` outside the `try`,
  so a throw there in the one-macrotask detached window is an unhandled rejection
  with no `notifyError`. Pre-existing; this fix makes that window load-bearing.
- `muiFree.test.ts`'s new walk is POSIX-only — the exception is spelled
  `'trackControl/MuiTrackControl.tsx'` and `readdirSync` yields platform
  separators. It also only catches *direct* naming of the barrel.
- Two commit-message inaccuracies worth not propagating: the PointerLayer commit
  swaps its call-site counts (three were on display-kit, four on display-ui), and
  its "53 KB-gzip edge" claim is not supported by the import graph — the deleted
  leaf was never on a weight-path entry.
