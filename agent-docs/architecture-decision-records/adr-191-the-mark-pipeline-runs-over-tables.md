# ADR-191: The mark pipeline runs over tables

## Status

Accepted (2026-09-28). The first of three landings, with
[ADR-192](adr-192-a-span-answers-a-hover-by-its-row.md) and
[ADR-193](adr-193-an-adapter-answers-the-mark-pipeline-its-typed-arrays.md),
of the table pipeline, which Colin asked to be built as the ideal system rather than a shim after
[ADR-190](adr-190-the-maf-display-stays-off-the-feature-steps.md) found the
Feature steps taking seconds where the MAF display takes tenths.

## Context

The mark display's worker ran a declaration as steps over `Feature` objects:
each step that made rows made one object per row (`DerivedFeature`,
`MadeFeature`, `FlattenedFeature`), the facet split them into arrays per
section, and the encoder walked the last list calling `get` per channel. The
steps' rules were never the cost; ADR-114, ADR-118, ADR-152 and ADR-190 each
priced a port and found the object per row.

## Decision

- **A step hands the next a table** (`packages/core/src/util/featureTable.ts`):
  a row count, a column per field resolved once by kind, and a row as a
  `Feature` only where something needs one — a `jexl:` expression, a channel
  reader, the hover. A column is a `number` lane a step wrote, a `category`
  (codes into labels), a `feature` column read off the parser's own objects, or
  a `value` a step computes per row, so a kernel picks its loop before the loop
  runs.
- **A table stands on another's rows.** A derived row records its parent row,
  and a field it lacks reads through to the parent's, with the index composed
  rather than a reader chained. A row is either the same row with fields beside
  it (`filter`, `formula`, `bin`, `pileup`, `mate`), whose `parent()` is its
  parent row's, or made from its parent row (`flatten`, `cells`), whose
  `parent()` is that row. The adapter's features filtered or reordered are
  still a table over those features.
- **Every step is one kernel over tables**, answering its rows in the order,
  with the ids and hover JSON, the Feature step answered. `cells` writes its
  runs as typed lanes and reads `base`, `match` and `length` back out of the
  texts only when asked; `flatten` over records keyed by name answers its key
  as a category; `bin`, `aggregate`, `coverage` and `pileup` write typed lanes,
  `pileup` sorting without a comparator where the start fits.
- **The facet is a partition**, a counting sort into section order, and a
  grouping step groups within each section's range. **`layerTables` splits a
  request as early as its steps allow**: after the last shared step that must
  see every row, since a step after it that reads a row and answers rows of it
  in order without writing the field answers the same rows either way. Over
  `marks_maf_cells` that splits the species rows behind `flatten`, so `cells`
  writes each species' runs together. `layerFeatures`, the row-matrix RPC and
  the marks test harness run a request through it.
- **The encoder reads rows by index.** `encodeFeatures` takes a table or a
  feature list, which becomes a source table; each channel compiles against
  its column, a constant colour reads no row, and a categorical colour over a
  category resolves each label once.
- `runTransforms` and `facetLayers` answer tables, and `FacetedLayer` carries
  `table` where it carried `features`: a plugin ABI break, taken before v5
  ships, with no caller in this tree or the store plugins' checkouts.

The steps that make rows are where the object per row was: a binned count in
0.33x<!--m:mark-pipeline-tables.bin-count.headVsBase--> of main's time, a
`formula` in
0.59x<!--m:mark-pipeline-tables.formula.headVsBase-->, the MAF declaration in
0.36x<!--m:mark-pipeline-tables.maf-cells-470-species.headVsBase-->. `coverage`
and `pileup` sit within a tenth of main, at
1.11x<!--m:mark-pipeline-tables.coverage.headVsBase--> and
1.10x<!--m:mark-pipeline-tables.pileup.headVsBase-->. The row furthest behind is
the facet over plain features, at
1.40x<!--m:mark-pipeline-tables.rows-by-sample.headVsBase-->: the encode reads
each feature once per channel where main read it once per row, and
`SimpleFeature.get` stays a call of its own where main's reader inlined it. A
second, feature-shaped encode loop would close it and is the shim this design
refuses; the row lookup that comes next takes the hit index off that same
request, which costs more than the difference.

## Consequences

- The step suite's tests and every suite over the pipeline pass, reading the
  tables back row by row where they asserted on feature lists.
- What the next landings take on is in the idea doc: the row lookup that
  spares a span under `rows` its hit index, and typed sources (the BigWig
  adapter's arrays, the MAF worker's arena) with `featureIndex` declined where
  it is the identity.
