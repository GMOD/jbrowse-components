# ADR-100: An index every reader shares is kept alive

## Status

Accepted

## Context

`TracksManagerSessionMixin` (`packages/product-core/src/Session/Tracks.ts`)
derives one index, `tracksByIdRecord`, mapping trackId to config across four
sources: the frozen `jbrowse.tracks` entries, each assembly's `sequence` track,
each temporary assembly's, every live connection's tracks, and the persisted
configs of opened connection tracks. Building it walks all of them.
`getTrackById(id)` layers a per-id `computed` over that index so resolving one
track's config subscribes only to that id — editing track A leaves track B's
observers alone.

Its comment said the index was "cached, so the N per-id lookups below share one
rebuild per change rather than each re-scanning." That was true only while
something observed it. A MobX computed with no observer does not cache: outside
a batch and with an empty observer set, `ComputedValue.get()` computes and
throws the result away, every call. Inside a reaction it caches, and inside an
MST action it caches too, because an action is a batch.

That divide is why nothing caught it. Every reader in the tree was on the caching
side by accident of where it ran — `TrackConfigurationReference`'s `get()`
resolves during an observed render, `showTrackGeneric` runs inside an MST action.
The one caller that is neither is search: `unanimousResult`
(`plugins/linear-genome-view/src/searchUtils.ts`) ranks its hits from an async
handler, in no observer and no action, and `trackRank` reaches `getTrackById`
once per hit. Every one of those calls re-walked every track in the session.

The first row is a separate defect in the caller, fixed alongside: the pick is a
stable minimum and `unanimousResult` was sorting the whole result array to take
`[0]`, so a comparator asked `getTrackById` O(n log n) times for an answer that
does not vary. Ranking once per hit is what the line above it already did for
`destinations`. The second row is this decision, and it is the larger half.

## Decision

Declare the index `computed(..., { keepAlive: true })`.

The index is one object per session, its dependencies are that session's own
observables, and it is created in the mixin's `.views()` closure, so it lives and
dies with the session that owns it. Invalidation stays MobX's and is unchanged: a
track added after the first read resolves, and the entries beside it keep their
identity, which is what the per-id computeds rely on to stay quiet during a
sibling's edit.

`keepAlive` makes the computed observed, so it is invalidated when its inputs
change but still recomputed lazily on the next read. Holding it alive costs a
recompute nobody asked for only if nobody reads it again, which for a session's
track index is not the case.

## Rejected: fix the caller

Wrapping the ranking in `runInAction`, or reading the whole record once through
`getTracksById()`, gets the same number for that one function — the diagnostic
arm in the notes above is exactly this. Both were rejected for the same reason:
they fix the reader that was found and leave the trap for the next one, and the
trap is invisible. The comment on the index already claimed the property, so the
next author outside a reaction has no way to learn otherwise short of profiling.

`getTracksById()` is additionally `@deprecated` for subscribing its caller to
every track. That warning is about reactive callers and would not have bitten
here, but reaching for a deprecated API to get a property the non-deprecated one
should already have is the wrong lesson to leave in the tree.

## Rejected: document it instead

The failure mode was a comment asserting a property the code did not have. A
second comment explaining when the first one is true is not a fix.

## Rejected: a hand-rolled cache with a version counter

This repo's bar for a memo is a measured win *and* an invalidation story. The
win is here, but the invalidation story is only free because MobX already keeps
it correct across four independent sources, two of which (`connectionInstances`,
`connectionTrackConfigs`) come from a mixin not every session composes. Restating
that by hand is how the two drift.

## Consequences

- The per-id computeds in `trackByIdComputeds` are still unobserved and still
  re-evaluate on every read. That is now a property lookup on a cached record
  rather than a full walk, and it is what keeps per-id reactivity intact.
- A reader outside a reaction no longer has to know any of this, which was the
  point. `getTrackById` costs what its name implies from anywhere.
- The record and its dependency links are retained for the session's lifetime.
  One object; the configs it indexes are already retained by the session.
- ADR-031 is the sibling decision about the *other* config cache — hydration of
  frozen tracks, scoped to the `PluginManager`. They are independent: that one
  exists because MST's custom references do not memoize at all, this one because
  a MobX computed does not memoize while unobserved.

## Revisit if

- MobX changes how an unobserved computed behaves, which would make `keepAlive`
  either redundant or insufficient rather than the exact fit it is now.
- The index grows an input expensive enough to retain that holding it alive costs
  more than rebuilding it. All four sources today are already session-retained.
