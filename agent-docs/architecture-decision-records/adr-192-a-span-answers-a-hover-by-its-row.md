# ADR-192: A span answers a hover by its row

## Status

Accepted (2026-09-28). The second landing of
[the-mark-pipeline-runs-over-tables](../ideas/ready/the-mark-pipeline-runs-over-tables.md),
behind [ADR-191](adr-191-the-mark-pipeline-runs-over-tables.md).

## Context

Every mark that answers a hover asked the worker for a Flatbush over its
instances, and the display searched it for the pointer's bp window across
every row before the mark's own ink test kept the nearest. After ADR-191 the
Flatbush was the largest single cost of a MAF request at 470 species, and the
mark display rebuilt it on the main thread whenever a species was hidden
(`facetLayer` in `plugins/marks/src/LinearMarkDisplay/facet.ts`). A span only
ever stands in its own row, so the question a hover asks of a span layer is one
row's, and a spatial index over every span answers a larger question than
that.

## Decision

- **`rowSpanIndex` in `packages/render-core/src/marks/rowSpanIndex.ts`**: a
  layer's spans counting-sorted by row, each row in start order (a row the
  pipeline left nearly in order, as `cells` does with an insertion ahead of the
  run it interrupts, is put right by insertion; one further out, by a
  comparator-free sort), with the furthest end the row has reached at each
  position. `spansInRow` answers a row's spans meeting a bp window with a
  binary search and a walk back that stops where no earlier span reaches the
  window, as a search over every span would.
- **The span spec answers by rows** (`hit: 'rows'` in `markSpecs.ts`), so a
  span layer asks the worker for no `index` lane. The other marks keep
  `hit: 'index'`: a bar, point or rule stands at a value, a link spans rows.
- **`findMarkHit` builds the index the first time a hover asks** and keeps it
  per layer, and asks it for every row whose band lies within the hit radius of
  the cursor, read back through the row table where one binds keys to slots.
  A row focus that hides species makes a new layer, and so a new index, with no
  Flatbush to rebuild.

The first hover over a region builds its index on the main thread: over the
5.5M runs of the 470-species region that took 169 ms where the Flatbush took
1390 ms in the worker (the record's notes), and a query stays a few
microseconds. The build is linear in the spans, so a region a cells view
shows builds in proportion.

## Consequences

- The facet over plain features that ADR-191 left behind main now runs at
  0.60x<!--m:span-row-lookup.rows-by-sample.headVsBase--> of the table pipeline
  with the index.
- The remaining landing is typed sources — the BigWig adapter's arrays and the
  MAF worker's arena — with `featureIndex` declined where it is the identity.
