# ADR-091: A track type is not a spec, and a display's settings are not a declaration

## Status

Rejected (2026-08-24), and this ADR rejects
[ADR-089](adr-089-a-track-type-is-a-spec-the-factory-composes-the-stack.md)
and [ADR-090](adr-090-a-mark-is-a-shape-plus-its-channels.md) with it. The
factory (`defineDisplay`), the mark system (`display-kit/marks`,
`render-core/marks/bar`) and `example-plugins/score-example`'s spec form are
removed; the example plugin is back on the hand-composed stack it had before
ADR-089, and the developer guides teach that again. Written against
the plan measured in [display-complexity-census](../reference/DISPLAY_COMPLEXITY_CENSUS.md), whose one surviving level landed in the narrow form
[ADR-096](adr-096-a-bands-contract-is-a-type-its-allocator-is-a-function.md)
records — the band contract as a type, the allocators still functions.

**The port and the settings table were measured on a working branch that no
longer exists.** This ADR cited `worktree-manhattan-lazy-spike` (29 commits) as
"the record"; `git for-each-ref` finds no branch, remote or tag under that name,
and `agent-docs/measurements/` had no entry. So there is no record to consult.

The eager closure is re-derived below from the commits that did land, and is the
one figure here a reader can check. Every other measurement is marked
**branch-only** where it appears: it describes code that existed only on that
branch, so it stands as the reasoning of the person who took it and cannot be
audited from this tree. None of them is the load-bearing one — the decision
turns on the shape of what the port needed, which the surviving `defineDisplay`
at `f0d8cf4e39` still half shows, and on the eager closure.

## Context

ADR-089 made a track type a spec handed to one factory, and ADR-090 let that
spec name a mark instead of a painter. Both were gauged on `score-example`: two
settings, no layout, one mark. ADR-089 was explicit that the in-tree stack was
unchanged. The idea doc asked the question it left open: can the factory hold a
real display, and can a display's settings be one declared table the schema,
the fetch key and the render state derive from? Level 0 tested it by porting
`LinearManhattanDisplay`, the smallest display with a real scale, hit test,
legend, tooltip, hand-written shader and `renderSvg`, against a budget
committed before the port.

The port fit: all 25 gwas suites passed with import changes only, and the
config docs page regenerated byte-identical. It was then measured:

- **Every field the port added to `defineDisplay` was an override hook**
  (branch-only). Six fields, each with exactly one consumer, each of the shape
  *let me override a piece of what you compose*: `rpc.inputs`, `renderState`,
  `extend`, `index`, `component`, `svgBody`. Of those, only `renderState` is in
  `defineDisplay.tsx` at `f0d8cf4e39`; the other five were added by the port and
  went with the branch. The domain half of the display (the LD model, the index
  SNP, both menus, ~478 lines against a 320-line budget) sat inside an imperative
  `extend`, and the RPC serialization (two `renameRegions` passes over adapters
  that disagree on contig spelling) could not be expressed at all. The pre-port
  commitment named this outcome as the falsifier: "if holding Manhattan requires
  a spec field per mixin hook, the imperative altitude is the real contract".
- **A state model is eager**, so everything a spec names by value loads at
  plugin install — the HAL, both renderer bases, `DisplayChrome` and the `bar`
  shader, for a display that draws points. See the table below.
- **Four generated censuses lost the display** (branch-only), two silently,
  because they key on `new DisplayType(`.
- **Lines were a wash** (branch-only): the display went 1,278 to 1,052 and the
  factory 431 to 658.

Both arms of that last one landed, which is what makes it re-derivable. The
factory names its chrome and its drawing by value;
`LinearManhattanDisplay/stateModelFactory.ts` keeps its component behind React
`lazy`. The difference between the two closures at `f0d8cf4e39`, the last commit
with `defineDisplay` alive, is what the spec form loads that the hand-composed
stack does not:

The branch's own figure was 40 modules and ~240 KB, taken against a real port of
Manhattan onto the factory rather than against the factory alone — the larger of
the two, and not re-derivable. The table is.

The port was reverted on the branch and the reusable half moved below the
factory as a data-only settings table (`params.ts`: slot definition plus an
`affects: 'fetch' | 'encode' | 'frame'` tag). That was measured too, and
**everything in this section is branch-only**: `params.ts`, `paramReader.ts` and
both converted displays existed only there, so none of these four can be
re-derived from this tree.

- **0 getters eliminated.** Both converted displays kept one hand-written getter
  per param; only the right-hand side changed. Deleting them moves the break to
  the display model's public surface, which menus, dialogs, renderers, SVG
  export and third-party plugins all read. The measured target was 60
  declarable getters out of 321, and the number removed was 0.
- **`affects` derives a correct fetch payload on 1 of 6 displays.** The values
  that invalidate a fetch are usually derived (a precedence ladder, a resolution
  against fetched metadata, an ordering) and raw-slot transport is the special
  case. The encode equivalent found 0 consumers in 2 displays and was deleted.
- **The table cannot hold meaning.** The deciding guard was alignments'
  `colorBy`: the table holds it as one `maybeFrozen` promotable slot and says
  nothing about the six-variant union with a nested six-field `modifications`
  object inside it. Deriving menu rows and legends from the table was not
  supported.
- **A shared setting acquires two owners.** The table owns the slot; a
  cross-cutting mixin (`LegendMixin`, `RowHeightMixin`,
  `WiggleScoreConfigMixin`) owns the accessor, the setter, the pin and the menu
  row. The tree's six such mixins already bundle slot, getter, setter, pin, menu
  row and dialog and retire that whole set across four to eight displays each,
  which is the better answer for the reducible half.

## Decision

**A display composes its own MST chain, in-tree or third-party, and its
settings live where they always did: a config schema, and typed getters
reading it through `getConf` / `resolveConf`.** There is no factory.

The bar this failed is whether a spec expresses a display's concepts natively
or holds them through escape hatches. It held them. That verdict does not stop
at the in-tree boundary: a third party with a real scale, a legend or a hit
test needs the same six hooks Manhattan needed, and a factory that can hold
only the wiring is a second way to write a display that is not simpler than the
first. Keeping it "for third parties" was the branch's rationalization, and the
only third party was the example plugin written to gauge it. The third-party
story is the one ADR-030 already made: the hand-composed stack, reached through
the published subpaths, which is what `score-example` shows again and what the
`plugin-vite` packed-tarball job guards.

A declaration that needs a function-valued option per display concept has
stopped being a declaration, and the branch's own don't-redo list (a
`transport:` field, a fourth `affects` value, a `normalize:` hook) is the list
of holes the next display would have needed.

## Consequences

Removed from the tree, by reverting `992f912ace` (ADR-089) and `f7471500e0`
(ADR-090):

- `packages/display-kit/src/defineDisplay.tsx` and `marks.ts`, and their
  published subpaths; `packages/render-core/src/marks/bar.ts` and the `bar`
  shader; `@jbrowse/core/configuration/configurationSlot` as a published
  subpath, which only the factory imported.
- `example-plugins/score-example`'s spec form. The plugin is back on
  `LinearScoreDisplay/` (model, config schema, renderer classes, component) and
  `ScoreRPC/`, which is the shape the developer guides walk through and the
  shape `component_tests/plugin-vite` smoke-tests from a packed tarball. Its
  `LinearScoreDisplay` config page is generated again. The **model** page was
  claimed here and in the revert's commit message and had never existed: the
  restored `model.ts` carried no `#stateModel` tag, so `pnpm autogen` produced
  nothing for it. The tag was added afterwards and the page exists now, which
  also puts the display back into the display-foundation census the ADR notes a
  spec form fell out of.
- `ideas/a-track-type-is-five-primitives`, the proposal behind all three, filed
  under `reference/REJECTED_IDEAS.md`.

Salvaged onto main from the branch, each independent of the declaration and
each found there by a check rather than a bug report:

- `symlogConstant` was read by `WiggleScoreConfigMixin` against hosts whose
  schema never declared it; it now lives on `WiggleCommonMixin`, whose hosts
  do.
- `RegionTooLargeMixin` read `fetchSizeLimit` and `forceLoad` off
  `baseLinearDisplayConfigSchema` while five composers did not extend it; the
  pair is now the mixin's own field table (`regionTooLargeConfigSchemaFields`),
  spread by the base schema and by those five, on the `RowHeightMixin` +
  `rowHeightConfigSchemaFields` precedent. This advertises two `advanced` slots
  on `LinearWiggleDisplay`, `MultiLinearWiggleDisplay` and
  `LinearReferenceSequenceDisplay` that do nothing while those displays leave
  the byte gate off; that is the cost of a mixin owning its slots, and an
  `undefined` budget is a gate that never fires the moment one turns it on.
- `BaseTrackModel.textSearchAdapter` read a top-level slot that lives at
  `textSearching.textSearchAdapter` and answered `undefined` for every track
  ever configured with one; `refNameMismatch` read a raw `assemblyNames` slot
  that `ReferenceSequenceTrack`'s schema omits and was inert for that track
  type.
- A worker payload could be built from an unresolved config snapshot;
  `ResolvedConfigSnapshot` is a brand the resolving reader applies and the
  payload builder requires.

Not salvaged, and why:

- **The composition-walk checks** (`compositionChains.ts` and the three tests
  over it, ~2,500 lines in `products/jbrowse-web/src/tests/`). They found the
  four defects above, and they are a source-parsing walk of every display's
  mixin chain standing in for what tsc already does for 18 of 19 promotable
  slots through `ConfigurationSlotValue` and for every host cast through
  `HostChecksSlotNames`. The population they reach that tsc does not is the
  bare `getConf(self, 'x')` on a widened holder, and
  `scripts/configReadTypeGaps.txt` is the committed list of those, whose header
  has always asked for the parameter to be narrowed rather than for a second
  checker. The branch's own handoff measured that 103 of its 125 remaining
  entries sit outside any composition chain — branch-only, and against a
  snapshot of that file, which lists
  286<!--m:config-read-type-gaps.all.unchecked--> unchecked reads here today.
- **`params.ts`, `paramReader.ts` and the converted Manhattan and HiC
  declarations.** The table above.

One finding outlives the factory as a constraint on any future authoring
surface: **a state model is eager**, so anything registered at plugin install
loads everything it names by value. A spec form that wants to be cheap has to
make its drawing loadable late, and the branch had to add `lazy()` thunks to
get there.

## Rejected alternatives

- **Keep `defineDisplay` for third parties only**, rejecting just the in-tree
  port and the table. The first draft of this ADR did that. Rejected above: the
  spec holds wiring only, its sole consumer was our own gauge, and the
  hand-composed stack through published subpaths is the third-party contract
  already.
- **Grow the factory a field per pull.** The shape has no bound, and each field
  ossifies into third-party ABI.
- **Resolving the declaration into a bag on the model** (`declaredParams`).
  Reading settings through a loop erases the types the config readers derive,
  and four pieces of machinery grew to buy them back. Reverted on the branch.
- **A `transport:` field, a fourth `affects` value, a `normalize:` hook.** Each
  is the escape hatch a declaration grows when it meets the next display.
- **A tree-wide check that promotable slots are read with `resolveConf`.**
  Redundant with the compile-time guard for all but three shapes.

## What would reopen this

Not a smaller display that fits. The next attempt has to start from the
display that does not: hold alignments' `colorBy`, or Manhattan's LD model and
dual-rename RPC, without an `extend`, and stay lazy. Nothing short of that is
evidence against what was measured here.
